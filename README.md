# Lab 05 - Event-Driven Document Enrichment & AI Integration

## Overview
This project extends the File Management platform (developed in previous laboratories) by transforming it into an intelligent and **Event-Driven** system.
The primary goal is the integration of **Spring AI** to automatically enrich uploaded documents with metadata generated by LLMs (Large Language Models) and enable **RAG (Retrieval-Augmented Generation)** capabilities, while ensuring robustness and scalability through **Apache Kafka** and the **Transactional Outbox** pattern.

##  System Architecture

The system consists of the following microservices and infrastructure components:

### Microservices
1.  **FileService (Kotlin/Spring Boot):** Manages file uploads (TUS protocol), file versioning, and access rules (ACL). It acts as the *Producer* of upload events via the Outbox pattern.
2.  **AIProcessingService (Kotlin/Spring Boot):** A new autonomous microservice acting as a Kafka *Consumer*. It is responsible for:
    * Downloading files from the FileService.
    * Interacting with the LLM (e.g., Gemini/OpenAI) to generate summaries, tags, and sensitivity analysis.
    * Generating *Embeddings* and saving them to the Vector Store.
    * Responding to user RAG queries.

### Infrastructure
* **Apache Kafka:** Message broker used to decouple file uploads from AI processing.
* **PostgreSQL + pgvector:** Relational database doubling as a **Vector Store** for semantic search.
* **Debezium (Kafka Connect):** Implements the *Transactional Outbox* pattern by reading the `outbox` table in the DB and automatically publishing events to Kafka.
* **Keycloak:** Manages identity and Machine-to-Machine (M2M) authentication between services.
* **MinIO:** S3-compatible object storage for physical files.

##  Key Features

### 1. Event-Driven Architecture & Outbox Pattern
To ensure data consistency (At-Least-Once delivery), we do not publish messages directly to Kafka from the application code.
* When a file upload is finalized (`UploadServiceImpl`), we save the file entity and a record in the `outbox` table within the **same database transaction**.
* **Debezium** captures changes to the `outbox` table and publishes the event to the `file-upload.completed` topic.
* This guarantees that no events are lost, even in the event of a broker or service crash.

### 2. AI Metadata Enrichment
Upon receiving an event, the `AIProcessingService`:
1.  Authenticates with the FileService using the **OAuth2 Client Credentials** flow.
2.  Downloads the file content.
3.  Sends the text to the LLM with a structured prompt.
4.  Receives and saves the following metadata to the DB:
    * **Summary:** A concise summary of the document.
    * **Tags:** Extracted keywords.
    * **Sensitivity:** Automatic classification (PUBLIC, INTERNAL, CONFIDENTIAL).

### 3. RAG (Retrieval-Augmented Generation) & Security
We implemented a secure "Chat with your Data" feature:
* Documents are split into *chunks* and transformed into vectors.
* When a user asks a question, the `FileService` first calculates a **Whitelist** of file IDs the user has access to (based on Owner, Department, and Shares).
* This list of IDs is passed to the AI Service, which uses it as a mandatory **filter in the Vector Store** (`fileId in [...]`).
* The LLM generates a response using *only* the context of files visible to the specific user.

## 🛠️ How to Run Tests

The project includes a comprehensive suite of automated tests. Since we use **Testcontainers**, you do not need to manually install databases or Kafka on your machine, but **Docker must be running**.

## 🧪 Testing Strategy
We implemented a robust testing strategy using JUnit 5, Mockito, and Testcontainers to validate the distributed nature of the system. The tests cover integration, security, and resilience scenarios.


### 1. Kafka Integration & Consumer Logic
File: AiKafkaConsumerTest.kt

Verifies that the AIProcessingService correctly connects to the Kafka broker, consumes messages from the file-upload.completed topic, and triggers the internal business logic. We use a Spy bean to verify the listener invocation without mocking the entire infrastructure.


### 2. Transactional Outbox Pattern
File: FileServiceOutboxTest.kt

Validates the producer side of the architecture. It ensures that when a textual file is uploaded, an event is strictly written to the outbox database table within the same transaction. It also verifies that non-textual files (e.g., images) do not trigger events.




### 3. Machine-to-Machine (M2M) Security
File: AiSafetyAndSecurityTest.kt

Verifies the Zero-Trust security model. The test intercepts outgoing HTTP calls from the AI Service to the File Service (for downloading files or updating metadata) and asserts that the Authorization: Bearer header is present and contains a valid OAuth2 token.



### 4. Resilience & Idempotency
File: AiIdempotencyTest.kt

Retry Mechanism: Simulates transient failures (e.g., network glitches) and verifies that the system retries the operation according to the configured BackOff policy before giving up.

Idempotency: Simulates the arrival of duplicate Kafka messages. The test ensures the system processes the request multiple times without crashing or corrupting the state.


### 5. RAG & Vector Store Integration
File: AIProcessorIntegrationTest.kt

Performs a full integration test of the RAG pipeline. It verifies that documents are correctly chunked, embeddings are generated (mocked LLM), stored in the PostgreSQL vector database, and correctly retrieved via similarity search.
